# Grounded relationship candidates

The relationship pipeline extracts a specific predicate and a sentence identifying the subject and object. `semantics.version = 2` retains direction, category, an independent relationship track, ongoing/event scope, active/ended state, assertion status, attribution and exact page/quote/UTF-16 offsets. Canonical endpoint sorting also reverses a directional arrow. Family, employment and feelings between the same people can coexist; an event has its own source anchor.

**2026-11-18 — relations only.** The relationship graph holds standing relations only: family, social ties and one character's feeling/attitude toward another (love, hatred, jealousy, suspicion, trust, fear). One-off actions (holding hands, trying to rescue, visiting) are events for the timeline, not relations. The questionnaire asks whether the evidence describes a lasting relation and the type table contains no action types; `verifyPairLabels` holds one-off answers (and legacy `kind=action`/`temporal_scope=event`) as `one_off_action` and `validateGroundedChapter` holds them for review; `graph.service.ts` drops already-stored action/event rows from edges and history. The DB constraint and types keep the `action`/`event` values for existing rows (additive-only rule).

A valid source quote and a complete schema are **structural checks, not proof that the interpretation is true**. Reversed feelings, misleading quoted speech and literary inference still need semantic review. Accepted candidates remain unpublished until that review. Legacy rows have no inferred direction or invented explanation.

## How relationships are generated (2026-11-18)

There is one relationship generator: structural candidates + an evidence-window **relation questionnaire** over a **closed relation-type table**, run on the **Claude subscription** (Claude Code CLI). The old path in which an LLM read a whole chapter and chose pairs (`run-generate-relationships.ts`, `buildRelationshipPrompt`, the OpenAI `generate_relationship` model setting, and the relationship calls inside `run-generate-full.ts`'s chapter cache) was deleted on the CEO's instruction of 2026-11-18. Chatbot, recap and the other batch generators (summary, characters, terms, events, background, reader text) still use the configured API provider.

- **Model calls.** Gateway tasks `generate_relationship` (questionnaire) and `generate_relationship_verifier` (adversarial verifier) never go to an API provider. `modules/llm-gateway/claude-cli-provider.ts` runs `claude -p --output-format json` with the prompt on stdin, no tools, no MCP, no session persistence, an empty temporary working directory, and a child environment without `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`/`OPENAI_API_KEY`, so the CLI uses the logged-in subscription. Timeout, retries (not on authentication failure) and the `[LLM Metrics]` log line (`provider: claude-cli`) are kept. A CLI failure fails the run; it never falls back to an API key. Settings: `CLAUDE_CLI_MODEL` (default `opus`), `CLAUDE_CLI_TIMEOUT_MS`, `CLAUDE_CLI_MAX_ATTEMPTS`, `CLAUDE_CLI_EFFORT`, `CLAUDE_CLI_BIN`. Tests replace the CLI with an injected runner or a fake `CLAUDE_CLI_BIN`.
- **Type table.** `batch/pipeline/relationship-taxonomy.ts` holds 24 relation types (family, romance, social, professional, adversarial, attitude), each with a definition, a yes/no decision question, exclusion questions, directionality (symmetric or subject → object) and literature sources. Rationale and confirmation levels: `docs/context/research-2026-11-18-relationship-classification.md`.
- **Questionnaire.** For each candidate pair the model answers, in order: is this a lasting relation (not a one-off action), coarse category, type key from the table, the type's decision question, its exclusion questions, subject (directed types), assertion status/attribution, state/change, summary, rationale, support (window id + exact trigger).
- **Code checks** (`interpretAnswer` + `verifyPairLabels`): type outside the table, decision question not `true`, any exclusion `true` or unanswered, subject outside the pair, or a one-off action → held. Coarse kind, label, `relation_key`, direction (`undirected` for symmetric types, `a_to_b` with the subject as `character_a` for directed types) and `temporal_scope` are **derived from the table, never taken from the model**. A category answer that disagrees with the type is stored per the table and flagged `category_answer_mismatch`; transitions/disclosures/ended states are flagged `change_needs_review`. Self-consistency requires the same pair, direction **and type** in both runs. Everything from the earlier structural design below (candidate pairs, trigger sentence, factuality cues, Korean case-particle direction check, earliest verified evidence page) is unchanged.
- **Mystery-specific public/secret relations** (Conan) are expressed with `assertion_status` + `attribution` (who says or believes it), not as separate types.

`run-generate-full.ts` (also used by the admin upload job) runs the same structural chapter step after merging each chapter's characters, with cache files `chapter-N.rel-structural.run-{1,2}.json` / `.verifier.json` sealed by the questionnaire/type-table/model contract. A machine without a logged-in `claude` CLI (for example the API server) fails at the relationship step instead of using another provider. `provenance.relationship_coverage` still proves source coverage, **not exhaustive extraction recall**. A changed existing resolved artifact is written as a separate candidate, preserving previous manual corrections.

## Staging a complete replacement

1. Apply the additive relationship-semantics migration in the intended environment.
2. Generate all chapters, inspect held candidates, and review the new full artifact. Existing character IDs must be explicitly reconciled with reviewed identities. Do not regenerate or overwrite existing character/alias corrections to make IDs match.
3. The initial-import command continues to reject existing content by default. For a deliberate complete relationship replacement, use:

   ```sh
   npx ts-node src/batch/pipeline/run-register-content.ts --replace-relationships
   ```

   This existing command targets the full Takryu artifact. The reusable `replaceRelationshipSnapshot` function accepts any book's complete artifact. It verifies the sealed exact stored source, complete chapter coverage and existing endpoint IDs. Partial samples, an empty replacement, duplicate IDs and unmapped endpoints fail before writes. The transaction stages only relationship changes, removes obsolete relationship IDs, invalidates prior relationship approvals, and sets the book unready. It preserves character, alias and note records. A before/after audit is written before commit.
4. Export the review sheet. Inspect direction, specific meaning, assertion/attribution, time/state and quoted evidence. A v2 approval is bound to the exact relationship snapshot. Changed content and old label-only approvals cannot satisfy publication. A v2 semantic correction requires a new reviewed candidate; editing only its label is insufficient.
5. Apply review judgments and separately run the existing publication check. Failed or incomplete review keeps the book unavailable.

Any registration or correction of already public generated content clears readiness before mutation. Replacement and approval application use transactions. The live public database is not changed by local extraction, tests, evaluator fixtures or a local database demonstration.

## Reporting verification

Report code checks, real model generation, public-data mutation, and deployment separately. A passing test does not prove a model ran; a hand-authored source-grounded fixture is not model output; a local database is not the public content store. Failed authentication must be reported as failed generation, even when the environment reports a configured key. Preserve actual source/evidence reports and never substitute synthetic success.

## Structural candidates + evidence-window labeling (2026-11-18)

`run-generate-relationships-structural.ts` is the literature-based generator (see `docs/context/research-2026-11-18-relationship-extraction.md`). Characters/aliases come from the existing extraction (`all-resolved.json`) or from a characters JSON passed with `--characters` (for example values read from the production database). `interaction-candidates.ts` deterministically proposes pairs only where two characters co-occur in a sentence, in adjacent sentences, or in an attributed dialogue exchange (no LLM). The LLM sees only those pairs, their evidence windows and the relation-type table, and must cite a window id plus an exact trigger inside it. `relationship-labeling.ts` rejects pairs with no structural candidate, checks that the trigger sentence names both endpoints, holds `fact` labels whose trigger clause/sentence carries negation, reportative, modal or source cues (or is refuted in the next sentence), and holds clear reversed directions (Korean case particles, English word order). **The established page is the earliest verified evidence page; an LLM-claimed earlier page is ignored**, and when the two self-consistency runs disagree the later page wins. Output then passes the existing `validateGroundedChapter` contract, optional adversarial verifier, `mergeRelationships`, and the same review/replacement flow above. No schema change. Characters that co-occur often but end with no relationship are listed in `uncovered_characters` for review (no relationship is invented).

```sh
npx ts-node --transpile-only src/batch/pipeline/run-generate-relationships-structural.ts --input source.json --out data/generated/structural/new-run
npx ts-node --transpile-only src/batch/pipeline/run-generate-relationships-structural.ts --book <bookId> --file <raw.txt> [--characters chars.json] [--verifier] [--candidates-only] [--out dir]
```

The report (`structural-relationships.json`) records accepted relationships with type, kind, direction, assertion, quote and established page, `held` items with reasons and `held_reasons` counts, `uncovered_characters`, and `counts.model_calls`/`model_seconds` (subscription calls actually made; cache replay is 0). Example run: `docs/validation/2026-11-18-relationships-claude/`.

Structural checks still cannot prove a label's meaning: in the injected-candidate worst case (any window word as trigger) 6 of 13 wrong candidates pass, unchanged after the questionnaire migration. Semantic review remains mandatory.
