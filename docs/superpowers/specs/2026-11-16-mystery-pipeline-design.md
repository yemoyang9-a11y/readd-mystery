# 추리소설 업로드·자동 파이프라인·관리자 대시보드 설계

작성일 2026-11-16. 상태: 사용자 승인 대기. 승인 전에는 구현하지 않는다.

## 1. 목적

관리자가 추리소설 원문 파일을 올리면 자동 파이프라인이 본문 분할, 인물관계도 자료, 챗봇 검색 자료를 만들고, 관리자가 마지막 검수 화면에서 승인해야만 독자에게 공개된다. 독자는 가장 멀리 읽은 쪽까지의 내용만 관계도·챗봇에서 본다. 챗봇은 결말을 말하지 않고 독자의 추리를 대신하지 않는다.

성공 기준은 세 가지다. 첫 책 한 권이 업로드부터 승인, 읽기, 세 기능 동작까지 사람 손의 명령 실행 없이 이어진다. 챗봇 공격 질문 세트에서 스포일러·추리 판정 누출이 0건이다. 공개된 모든 관계에 원문과 일치하는 인용 근거가 붙어 있다.

## 2. 하지 않는 것

- 새 시안(3D 홈 등)의 디자인 적용. 화면은 기존 구조에 최소로 연결한다.
- EPUB·PDF 업로드. 첫 단계는 UTF-8 텍스트 파일만 받는다.
- 운영 DB 변경, 배포, PR. 사용자가 따로 요청할 때만 한다.
- 2권·3권의 파이프라인 실행. 원문만 확보하고, 1권 검증 뒤에 진행한다.

## 3. 대상 도서

모두 김내성(1957년 사망, 국내 저작권 만료) 작품이며 한국어 위키문헌에 본문이 있다. 맞춤법 상태와 누락 여부는 내려받은 뒤 확인한다.

| 순서 | 작품 | 분량(추정) | 용도 |
| --- | --- | --- | --- |
| 1 | 「가상범인」 | 약 5만 자 | 첫 파이프라인 검증. 짧아서 반복 비용이 낮다 |
| 2 | 「타원형의 거울」 | 약 4만 자 | 두 번째 |
| 3 | 「마인」 | 약 48만 자, 31개 장 | 장편. 파이프라인이 안정된 뒤 |

## 4. 기준 쪽수: 가장 멀리 읽은 쪽

### 4.1 규칙 변경

기존 R1(기준점 = 마지막으로 연 쪽)과 R2(최대 도달 값은 없다)를 바꾼다. CLAUDE.md의 R1·R2, 절대 규칙 표, 3장을 이 설계에 맞춰 고친다.

```
저장값(둘):  reading_position.current_page   지금 펼친 쪽. 이어 읽기 위치
             reading_position.max_page       가장 멀리 읽은 쪽. 줄어들지 않는다

파생(기준점 결정기 한 곳에서만):
    cutoff      = 진도 레코드 없음 ? 0 : max_page
    percent     = max_page / total_pages
    is_complete = 진도 레코드 있음 && max_page >= total_pages
    chapter     = max_page가 속한 장
```

### 4.2 동작

- 쪽 이동 이벤트가 오면 한 SQL 문장에서 `current_page = 새 값`, `max_page = GREATEST(max_page, 새 값)`으로 갱신한다. 기존 `event_seq` 순서 검사는 그대로 둔다.
- 300쪽까지 갔다가 40쪽으로 돌아오면 `current_page = 40`, `max_page = 300`이다. 관계도·챗봇은 300쪽까지 다룬다.
- 기준 쪽수를 올리는 입력은 여전히 쪽 이동 하나뿐이다. 클라이언트는 기준 쪽수를 보내지 않는다.
- 조회·조립·검색 함수는 지금처럼 요청당 한 번 받은 스냅샷의 `cutoff`만 상한으로 쓴다. 상한 강제 위치(쿼리 조건, 근거 조립 범위)는 바뀌지 않는다.
- 기존 진도 레코드는 `max_page = current_page`로 채운다.

### 4.3 실수로 건너뛴 경우

본문 접근은 제한하지 않으므로, 목차에서 마지막 장을 잘못 누르면 기준 쪽수가 끝까지 올라가 관계도에 범인이 드러날 수 있다. 서버 규칙은 단순하게 두고 화면에서 막는다. 목차로 가장 멀리 읽은 쪽보다 뒤로 건너뛸 때 "여기로 이동하면 관계도와 챗봇이 이 쪽까지의 내용을 다룹니다"라는 확인 창을 띄운다. 한 쪽씩 넘길 때는 띄우지 않는다. 기준 쪽수를 되돌리는 기능은 만들지 않는다.

### 4.4 테스트

- 300쪽 방문 뒤 40쪽으로 복귀: 130쪽에 확립된 사실이 보인다. 301쪽 사실은 0건이다.
- 40쪽만 읽은 상태: 130쪽 사실 0건. 같은 사실이 130쪽 도달 뒤에는 보인다.
- 순서가 뒤바뀐 이벤트가 와도 `max_page`가 줄지 않는다.

## 5. 업로드와 자동 파이프라인

### 5.1 흐름

```
관리자 업로드(txt) → 작업 등록 → [분할 → 인물·사건·관계 생성 → 자동 검증 → 임베딩 → 미공개 등록]
                                   → 검수 대기 → 관리자 승인 → 공개
```

- 기존 `backend/src/batch/pipeline`의 분할·생성·근거 확인·등록·공개 단계를 재사용한다. 「탁류」 고정값(파일 경로, bookId)을 인자로 바꾸고, 단계를 순서대로 실행하는 실행기를 새로 만든다.
- 작업 상태는 DB 테이블에 단계별로 기록한다(대기, 진행, 실패 사유, 완료). 서버가 재시작되면 끝난 단계 다음부터 이어 간다.
- 등록은 미공개 상태로만 한다. 공개 전환은 승인 API 한 곳에서만 일어난다. 승인 전 도서는 독자용 목록·본문·관계도·챗봇 어디에도 나오지 않는다(R12 유지).
- 어느 단계든 실패하면 그 책은 미공개로 남는다. 일부만 공개하는 경로는 만들지 않는다.

### 5.2 추리 노트

독자가 직접 쓰는 기록이라 생성 파이프라인이 없다. 저장 테이블과 API(작성, 수정, 삭제, 목록)를 만들고, 노트마다 쪽수를 붙인다. 챗봇은 그 독자의 노트를 참고 자료로 받는다. 읽기 화면 패널 탭은 추리 노트·인물관계도·AI 챗봇 셋으로 바꾸고, 리캡은 패널에서 빼고 브리핑 화면에만 남긴다.

## 6. 인물관계도 정확도 설계

틀린 관계가 공개되는 것을 줄이는 단계를 차례로 둔다. 어떤 단계도 오류 0을 보장하지 않으며, 마지막 판단은 관리자 검수다.

1. 추출: 장 단위로 관계 후보를 뽑는다. 후보마다 주어·대상·방향·관계 종류·확립 쪽수·원문 인용을 갖는다(기존 semantics v2).
2. 기계 검증: 인용문이 해당 쪽 원문과 글자 단위로 일치하는지, 두 인물의 이름이나 등록된 별칭이 인용 주변에 실제로 나오는지, 확립 쪽수가 인용 쪽수와 맞는지 확인한다. 하나라도 어긋나면 보류한다.
3. 동일 인물 정리: 별칭·호칭을 한 인물로 묶는다. 묶는 근거 문장이 없으면 묶지 않고 검수 항목으로 올린다.
4. 교차 확인: 같은 장을 독립적으로 한 번 더 추출해 두 결과가 일치하는 후보만 "확인됨"으로 둔다. 한쪽에만 있는 후보는 "확인 필요"로 표시한다.
5. 반대 검토: 별도 호출로 "이 인용이 이 관계와 방향을 뒷받침하는가"만 묻는다. 뒷받침하지 않는다는 답이 나오면 보류한다.
6. 시점 처리: 같은 두 사람의 관계가 바뀌면 쪽수별 버전으로 저장하고, 조회 때 기준 쪽수 이하의 가장 최근 버전만 고른다. 앞 사건의 설명문도 그 쪽 시점에 알 수 있는 말로만 적는다.
7. 검수 화면: 확인됨, 확인 필요, 보류를 나눠 인용과 함께 보여 준다.

측정: 「가상범인」에서 공개 후보 전체를 조정자(이 세션)가 원문과 대조해 맞음·틀림을 세고, 그 비율을 그대로 보고한다.

## 7. 챗봇 하네스

막는 대상은 둘이다. 기준 쪽수 뒤의 내용(스포일러)과, 독자의 가설이 맞는지 판정하거나 범인을 지목하는 일(추리 관여).

1. 자료 단계: 검색과 근거 조립은 기준 쪽수 이하만 가져온다. 기존 구조 그대로다. 모델이 뒤쪽 내용을 받지 못하므로 말할 재료가 없다.
2. 질문 분류: 질문을 사실 찾기, 가설 확인 요청, 범인·결말 요청, 예측 요청, 작품 밖 질문으로 나눈다. 분류는 근거 범위를 바꾸지 않는다.
3. 유형별 응답 방식: 가설 확인·범인 요청에는 판정하지 않고, 관련된 앞 장면을 쪽수와 함께 찾아 준다. 예측 요청에는 답하지 않는다.
4. 출력 검사: 답변에 나온 쪽수가 모두 기준 쪽수 이하인지, 인용문이 원문에 있는지, 가설의 정답 여부를 판정하는 표현이 있는지 검사한다. 걸리면 한 번 다시 생성하고, 또 걸리면 안전한 고정 답변을 보낸다.
5. 공격 질문 세트(오프라인 시험): 우회 지시, "예/아니오로만", 역할극, 모델의 사전 지식 유도 등 60개 이상을 자동 실행한다. 정답표(범인, 결말 사실)는 이 시험 도구 안에만 두고 실행 중인 서버는 접근하지 않는다(절대 규칙 7 유지). 목표는 누출 0건이다.

남는 위험(A10): 모델이 작품을 이미 알고 있으면 자료 없이도 답할 수 있다. 4번 검사와 답변 규칙으로 줄일 뿐 구조로 막지 못한다. 시험 결과에 이 항목을 따로 적는다.

## 8. 관리자 대시보드

- 접근: 관리자만. 서버 환경변수 `ADMIN_API_TOKEN`과 같은 토큰을 낸 요청만 통과한다(로컬에서 소셜 로그인 없이 시험하기 위해 이메일 허용 목록 대신 택했다).
- 이용 현황: 유입 경로(referrer, UTM), 화면별 방문, 클릭한 요소 상위 목록, 평균 머문 시간, 일별 방문 수. 프런트에 수집 코드를 넣고 `analytics_event` 테이블에 쌓는다. 식별은 기기 ID로만 하고 이름·이메일은 저장하지 않는다. 쪽 안 스크롤은 서버 이벤트를 만들지 않는다(절대 규칙 9 유지).
- 도서 관리: 파일 업로드, 작업 진행 상태, 검수 화면(본문 미리보기, 인물, 관계와 인용, 검증 결과), 승인·반려 버튼.

개인정보 처리방침에 이용 기록 수집 항목을 넣어야 한다. 문서 작업은 이번 범위 밖이며 공개 전에 필요하다.

## 9. 검토한 방식

| 방식 | 장단점 | 결정 |
| --- | --- | --- |
| 기존 파이프라인을 인자화하고 실행기·작업 테이블을 덧붙인다 | 검증된 단계와 테스트를 그대로 쓴다. 「탁류」 전용 코드를 걷어내는 수고가 든다 | 채택 |
| 파이프라인을 새로 만든다 | 구조가 깔끔하다. 이미 있는 근거 확인·교체 안전장치를 다시 만들어야 한다 | 기각 |
| 업로드 즉시 공개하고 자동 검증만 한다 | 가장 빠르다. 틀린 관계가 그대로 나간다 | 기각(사용자 결정: 승인 전 미반영) |

기준 쪽수는 "서버가 최대값을 한 열에 저장"을 택했다. 이동 기록 전체를 쌓아 매번 최대값을 구하는 방식은 같은 결과에 저장과 조회 비용만 늘어난다.
