## 재현하여 수정한 문제

우선순위: P1은 데이터/보호 규칙 또는 핵심 기능에 직접 영향, P2는 사용성·성능·유지보수 문제다.

### P1 — 원문 200자 검사에서 Unicode 위치가 어긋남

- 위치: `backend/src/modules/chatbot/harness/output-guard.ts`.
- 답변의 위치 배열은 코드 포인트, 문자열 잘라내기는 UTF-16 단위였다. 이모지 210개 뒤에 원문 201자를 붙이면 검사 위치가 어긋나 상한을 통과했다.
- 원문 n-gram·답변·위치 계산을 코드 포인트로 통일했다. 보조 평면 문자 200/201자와 이모지 접두사 회귀 테스트를 추가했다.
- 이는 정확 복사량의 계산 오류 수정이다. 의역·짧은 조각 누적·모델 사전 지식까지 해결한 것은 아니다. 기존 답변당 200자 정책을 유지한다.

### P1 — 실제 도서 범위를 넘는 진도와 대량 배열 생성

- 위치: `backend/src/modules/reading-state/progress.service.ts`, `backend/src/api/routes.ts`.
- `read_through`는 입력 page 길이의 배열을 만들었다. 도서 끝을 넘는 큰 양의 정수가 저장·메모리 사용량에 영향을 줄 수 있었다.
- 저장과 배열 생성 전에 도서 메타데이터로 page/from_page 범위를 검사하고, page/seq의 안전한 정수 여부를 검사한다. 잘못된 입력은 400으로 응답한다. 확인 카드에서 가져온 저장값도 범위를 검사한다.
- 회귀 시험: 범위 초과·소수·음수·매우 큰 정수, API 400, 손상된 저장값, 정상 마지막 쪽 수용. 기준점 계산은 계속 `cutoff.service.ts`만 담당한다.

### P1 — 재시도 중 생성 캐시가 다시 삭제됨

- 위치: `backend/src/modules/ingest/runner.ts`, `admin-router.ts`.
- 두 retry 요청이 겹치면 실행 잠금을 얻기 전에 양쪽이 캐시 무효화를 수행했다. 진행 중인 재생성 산출물을 다른 요청이 지울 수 있었다.
- 상태 확인·캐시 무효화·실행을 같은 프로세스 내 잠금으로 묶었다. 중복 요청 시 캐시 무효화 1회·단계 실행 1회를 시험한다. 라우터에서 비동기 작업의 최상위 실패도 처리한다.
- **다중 프로세스/인스턴스 잠금은 아니다.** 분산 실행은 아래 후속 과제다.

### P1 — 비루트 컨테이너에서 관리자 업로드 경로 생성 불가

- 위치: `backend/Dockerfile`.
- 런타임 사용자는 node인데 `/app`는 root 소유이고 `/app/data`가 준비되지 않았다. 업로드 시 하위 폴더 생성이 EACCES로 실패하는 구성이다.
- data 작업 폴더를 생성해 node 사용자에게 소유권을 준다. CI에 실제 이미지 빌드와 비루트 mkdir/touch 검사를 추가했다. 원문은 이미지에 포함하지 않는다.
- 쓰기 권한과 영속 보관은 다르다. 이 변경만으로 재배포 시 원문이 보존되지는 않는다.

### P2 — 메모 조회·저장·화면 전환의 응답 순서 경합

- 위치: `frontend/src/hooks/useNotes.ts`.
- 늦은 초기 목록이 방금 추가한 노트를 지우거나 삭제한 노트를 되살리고, 이전 책 저장 결과가 다음 책 화면에 섞일 수 있었다.
- 책별 요청 범위와 성공한 변경 기록을 분리한다. 목록이 늦게 와도 생성/수정/삭제를 병합하고 이전 책 결과는 적용하지 않는다. 세 가지 비동기 경합을 회귀 시험한다.
- 같은 노트에 대한 여러 수정 요청의 순서나 다른 기기 동시 편집 충돌까지 해결한 것은 아니다.

### P2 — 정상 완료와 스트림 연결 종료를 구분하지 않음

- 위치: `frontend/src/services/stream.ts`.
- terminal 이벤트 없이 EOF가 나도 정상 종료해 일부 답변이 완성본처럼 남을 수 있었다.
- done/error 이벤트를 종료 신호로 처리하고, 그 전의 EOF는 오류로 전달한다. 종료·취소 시 reader도 해제한다. 기존 상위 훅의 오류 처리로 부분 결과를 정리한다.
- 정상 완료·서버 error·빈 스트림·중도 종료를 시험한다.

### P2 — 모달 키보드 조작과 확인 실패 안내

- 위치: `useModalLayer.ts`, `TocJumpDialog.tsx`, `ReaderPrefsSheet.tsx`, `NotesTab.tsx`, `FrontierConfirmCard.tsx`.
- 최상위 모달에서만 Tab/Escape를 처리하고, 버튼 사이 초점을 순환시킨다. 취소를 처음 선택하고 닫으면 원래 요소로 초점을 돌린다. 리렌더링 때 입력 초점을 빼앗지 않는다.
- 높이가 작은 화면에서도 모달 내부를 스크롤할 수 있게 한다. 서버 확인 실패/예외 시 안내를 표시하고 재시도를 허용한다.
- 기존 캡처 `docs/validation/2026-11-17-read-frontier/03-toc-jump-dialog-390x664.png`에서 현재 3버튼 구성과 글자 밀도를 확인했다. **이 캡처는 수정 후 화면의 증거가 아니다.**

### P2 — 첫 화면에 읽기·관계도·관리자 코드까지 포함

- 위치: `frontend/src/App.tsx`.
- 읽기·브리핑·커뮤니티·관리자를 라우트 단위 동적 import로 분리했다. 첫 로딩에는 로딩 표시를 제공한다. 라우팅 테스트는 비동기 로딩이 끝난 실제 화면을 확인한다.
- 로컬 Vite 빌드의 주 진입 JS: **646.14 → 321.24kB**, gzip **203.75 → 108.41kB**. 같은 환경의 변경 전후 수치이며 네트워크 지연이나 LCP를 측정한 값은 아니다. 작업 중 main 기능 추가도 있었으므로 정밀 성능 비교는 동일 커밋 벤치마크가 필요하다.
- 읽기 화면을 열면 관련 청크는 여전히 필요하다. 전체 코드량을 절반으로 줄였다는 의미는 아니다.

### P2 — CI 검사 범위와 문서가 실제 구현을 따라가지 못함

- 기존 백엔드 린트 명령의 인용되지 않은 `src/**/*.ts`가 셸에서 확장되어 일부 디렉터리만 검사했다. `eslint src --ext .ts`로 생산 소스를 모두 검사하고, 별도 tsconfig가 없는 테스트는 Jest 타입검사로 검증한다.
- 프론트 린트 오류와 생산 소스 서식 오류를 수정했다. 관리자 API의 기본 any를 unknown으로 바꾸고 검수 누락 목록을 실제 구조로 검사한다.
- CI에 린트, 제한된 테스트 병렬 수, npm 캐시, 중복 PR 실행 취소, 휴대폰/PC smoke 12개, Docker 비루트 쓰기 검사를 추가한다. PR에서는 운영 배포를 하지 않는다.
- README/PRODUCT/컨텍스트 문서의 `max_page = cutoff`, 타임라인 미구현, 인용 상한 미병합 등의 오래된 설명을 현재 코드와 결정에 맞춘다. 새로운 제품 정책은 만들지 않는다.
